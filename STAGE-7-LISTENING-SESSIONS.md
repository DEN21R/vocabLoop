# Этап 7. Listening Sessions в базе

Продолжение [плана VocabLoop](./PLAN.md). Сессия — именованный набор слов, например «В аэропорту», с сохранённым порядком и интервалом между словами.

**Объяснение → ты пишешь → проверяем → следующий шаг.** Код приложения пишешь ты. Файлы создаём по мере работы, без новых библиотек и дополнительных слоёв.

## Что получим

Backend сможет создать набор, показать список наборов, открыть один и изменить его. После перезапуска приложения набор останется в MongoDB.

На этом этапе работаем с сервером и Postman. Интерфейс создаём на этапе 8, циклическое воспроизведение — на этапе 9. Завершение этапа 6А проверяем отдельно; этот документ не означает, что все его проверки уже пройдены.

## Простые правила

- Название: строка от 1 до 100 символов после удаления пробелов по краям.
- Слова: массив ID в порядке будущего воспроизведения, без повторов. Пустой набор разрешён: его можно наполнить позже.
- Интервал: `intervalSeconds`, целое число от 0 до 60, по умолчанию 3 секунды. Это будущая пауза после перевода перед следующим словом.
- Владелец берётся только из `req.user.id`, который устанавливает существующий `protect`.
- В набор можно включить только свои существующие слова.
- Храним ссылки на слова, а не копии переводов или аудио. Изменения слова будут видны при следующем открытии набора.
- Если слово удалено из словаря, пропускаем его при открытии набора. Остальные слова сохраняют свой порядок. Сессия может стать пустой.

## Шаг 1. Модель сессии

**Файл:** `server/src/modules/listening-session/ListeningSession.js`.

По примеру `Word.js` опиши схему и экспортируй модель `ListeningSession`.

| Поле                     | Тип и назначение                                      |
| ------------------------ | ----------------------------------------------------- |
| `user`                   | Обязательная ссылка ObjectId на `User`                |
| `name`                   | Обязательная строка, trim, максимум 100 символов      |
| `words`                  | Массив ссылок ObjectId на `Word`, по умолчанию пустой |
| `intervalSeconds`        | Число, по умолчанию 3, допустимо 0–60                 |
| `createdAt`, `updatedAt` | Через `timestamps`                                    |

Целое значение интервала проверим при приёме запроса. Не добавляем сюда логику плеера или настройки браузерных голосов.

**Результат:** схема написана и разобрана на ревью. После этого переходим к первому маршруту.

## Шаг 2. Создать набор

**Файлы:** `listeningSession.controller.js`, `listeningSession.routes.js` в той же папке; подключение роутера в `server/src/app.js`.

Маршрут: `POST /listening-sessions`, обязательно через `protect`.

Поля запроса:

```json
{
  "name": "В аэропорту",
  "words": [],
  "intervalSeconds": 3
}
```

Последовательность действий:

1. Проверить тело запроса и название.
2. Если `words` не передан — использовать пустой массив. Если интервал не передан — использовать 3. Значение 0 разрешено: не заменять его через `|| 3`.
3. Проверить массив ID: строки корректного формата ObjectId, без повторов.
4. Найти слова по переданным ID и `user: req.user.id`. Количество найденных слов должно совпасть с количеством ID; иначе вернуть 400 без сохранения.
5. Проверить, что интервал — целое число в пределах 0–60.
6. Сохранить только `user`, `name`, `words`, `intervalSeconds`. Массив ID брать из запроса, чтобы сохранить порядок.
7. Ответить 201 и `{ session: ... }`.

Не передавать весь `req.body` в модель. Проверки здесь нужны для конкретных вещей: чужие слова, неверные данные и порядок набора.

**Проверка:** создать набор с двумя своими словами. Чужой или отсутствующий ID должен дать 400; пустой набор — успешно сохраниться.

## Шаг 3. Список моих наборов

Маршрут: `GET /listening-sessions`, через `protect`.

Найти сессии по `user: req.user.id`, отсортировать по `createdAt` от новых к старым. Вернуть 200 и `{ sessions: [...] }`. Если наборов нет — пустой массив.

В списке достаточно документов сессий со ссылками на слова. Загружать содержимое всех слов и аудио здесь не нужно.

**Проверка:** созданный набор виден после нового запроса. Под другим аккаунтом он не появляется.

## Шаг 4. Открыть один набор

Маршрут: `GET /listening-sessions/:id`, через `protect`.

1. Проверить формат ID сессии; неверный формат — 400.
2. Найти сессию одновременно по `_id` и владельцу. Если её нет или она чужая — 404.
3. Получить связанные слова текущего пользователя.
4. Вернуть слова в порядке массива `session.words`. Отсутствующие слова пропустить.
5. Ответить 200 и `{ session: ... }`, где `session.words` содержит объекты слов, а не только ID.

Можно использовать `populate` с фильтром по владельцу и явным выбором полей слова: `_id`, `original`, `translation`, `sourceLanguage`, `targetLanguage`, `hasRecording`, `createdAt`, `updatedAt`. Байты `recordingData` не возвращаем.

Если получать слова отдельным запросом, не рассчитывать на порядок результатов `$in`: собрать ответ по исходному массиву ID.

**Проверка:** сохранить слова в порядке Б → А и получить Б → А. Удалить одно слово из словаря и снова открыть набор — оставшееся слово доступно, ошибки нет.

## Шаг 5. Изменить набор

Маршрут: `PATCH /listening-sessions/:id`, через `protect`.

Разрешённые изменения: `name`, `words`, `intervalSeconds`. Передаём только те поля, которые хотим изменить.

1. Проверить ID и найти сессию по ID и владельцу, как в шаге 4.
2. Проверять только переданные поля по правилам создания.
3. Если передан `words`, заменить массив целиком после проверки принадлежности слов. Пустой массив очищает набор, не удаляя слова из словаря.
4. Если поле не передано, оставить прежнее значение. Явно переданные `null` и неверные типы не считать отсутствием поля.
5. Если не передано ни одного разрешённого поля — вернуть 400.
6. Сначала проверить все изменения, затем записать их и сохранить сессию. Ответить 200 и `{ session: ... }` со ссылками на слова, как при создании.

**Проверка:** отдельно изменить название, интервал и порядок слов. После каждого изменения открыть сессию через GET. Чужое слово в обновлении должно дать 400 и оставить прежний набор.

Если одинаковые проверки создания и изменения мешают чтению, вынесем небольшую функцию в тот же файл. Заранее отдельные сервисы и валидаторы не создаём.

## Формат API

| Метод и адрес                   | Ответ                                           |
| ------------------------------- | ----------------------------------------------- |
| `POST /listening-sessions`      | 201, `{ session }`, слова как ID                |
| `GET /listening-sessions`       | 200, `{ sessions }`, слова как ID               |
| `GET /listening-sessions/:id`   | 200, `{ session }`, слова как объекты без аудио |
| `PATCH /listening-sessions/:id` | 200, `{ session }`, слова как ID                |

Ошибки возвращаем как `{ message: '...' }`: 400 — неверный запрос, 401 — нет авторизации, 404 — сессия не найдена у пользователя, 500 — неожиданная ошибка сервера.

## Когда этап готов

- [ ] Набор создаётся и остаётся в MongoDB.
- [ ] Список показывает только наборы текущего пользователя.
- [ ] Один набор открывается со словами в сохранённом порядке.
- [ ] Можно изменить название, состав, порядок и интервал.
- [ ] Чужие сессии и слова недоступны.
- [ ] Удалённое слово не ломает загрузку; пустая сессия разрешена.
- [ ] Интервал 0 принимается, дробный и выходящий за 0–60 отклоняются.

Проверки выполняем по мере шагов через Postman. Готового тестового набора на сервере сейчас нет. Удаление сессий, интерфейс и плеер не добавляем в этот этап.
