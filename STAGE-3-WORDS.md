# Этап 3. Слово и его сохранение в MongoDB

Этот материал раскрывает этап 3 из [PLAN.md](./PLAN.md). Используем структуру backend после этапа 2: `server/src/modules`.

Формат работы: читаешь объяснение одного шага → пишешь небольшой фрагмент самостоятельно → просишь ревью → проверяешь поведение → переходишь дальше. Ниже нет готовой реализации контроллеров и маршрутов.

## Что хотим получить

Авторизованный пользователь отправляет оригинал слова, перевод и языки. Backend проверяет данные, связывает слово с текущим пользователем и сохраняет его в MongoDB. Отдельным запросом пользователь получает только свои слова. После перезапуска сервера сохранённые слова остаются в базе.

На этом этапе перевод вводим вручную. Форму и список на frontend добавим на этапе 4, автоматический перевод через Google Cloud Translation API — на этапе 5. Сейчас проверяем API через HTTP-клиент, например Postman или Thunder Client.

## Как проходит запрос

Создание: HTTP-клиент → POST /words → protect → createWord → проверка полей → Word.create → MongoDB → ответ с сохранённым словом.

Получение: HTTP-клиент → GET /words → protect → getWords → поиск по владельцу → MongoDB → ответ со списком.

`protect` уже проверяет JWT и записывает ID пользователя в `req.user.id`. Контроллер слова использует этот ID. Проверка `/auth/me` на frontend не заменяет защиту маршрутов `/words`: к API можно обратиться напрямую.

## Слова, которые встретятся

| Понятие        | Что означает у нас                                      |
| -------------- | ------------------------------------------------------- |
| Документ       | Одна сохранённая запись слова в MongoDB                 |
| Схема          | Описание полей и правил проверки документа              |
| Модель         | Объект Mongoose, через который создаём и ищем документы |
| ObjectId       | Тип идентификатора документа MongoDB                    |
| Владелец       | Пользователь, которому принадлежит слово                |
| ref            | Указание модели, на документ которой ссылается поле     |
| Валидация      | Проверка, подходит ли ввод под правила приложения       |
| Контракт API   | Согласованные поля запроса, ответа и HTTP-статусы       |
| Фильтр запроса | Условие, определяющее, какие документы вернёт база      |
| timestamps     | Автоматическое ведение createdAt и updatedAt            |

## Шаг 1. Согласовать поля и контракт API

### Какие данные храним

Для этого этапа договоримся о следующих названиях:

| Поле документа   | Тип                         | Откуда берётся                              |
| ---------------- | --------------------------- | ------------------------------------------- |
| `_id`            | ObjectId                    | Создаётся при сохранении                    |
| `user`           | ObjectId со ссылкой на User | Из req.user.id                              |
| `original`       | String                      | Оригинал из запроса                         |
| `translation`    | String                      | Ручной перевод из запроса                   |
| `sourceLanguage` | String                      | Код языка оригинала из запроса, например en |
| `targetLanguage` | String                      | Код языка перевода из запроса, например uk  |
| `createdAt`      | Date                        | Через timestamps                            |
| `updatedAt`      | Date                        | Через timestamps                            |

Четыре текстовых поля обязательны. В начале и конце строк убираем пробелы, регистр оригинала и перевода сохраняем. На этом шаге проверяем, что коды языков — непустые строки; список поддерживаемых провайдером языков согласуем на этапе 5. Повторное добавление одинакового слова пока разрешено.

### Запрос создания

`POST /words` принимает JSON с четырьмя текстовыми полями. Пример данных для проверки, а не готовая реализация:

```json
{
  "original": "apple",
  "translation": "яблуко",
  "sourceLanguage": "en",
  "targetLanguage": "uk"
}
```

В заголовках нужны `Content-Type: application/json` и `Authorization: Bearer <токен>`. Вместо обозначения токена подставь токен своего учебного аккаунта только в HTTP-клиенте.

Клиент не назначает владельца, ID и даты. Если в JSON прислали дополнительные поля, контроллер их игнорирует: для сохранения он явно выбирает разрешённые поля.

### Ответы

| Запрос или ситуация                 | Статус | Тело ответа                     |
| ----------------------------------- | ------ | ------------------------------- |
| Слово создано                       | 201    | Объект с полем word             |
| Список получен                      | 200    | Объект с полем words — массивом |
| Слов пока нет                       | 200    | Объект с пустым массивом words  |
| Ошибка входных данных               | 400    | Объект с сообщением message     |
| Нет токена или он недействителен    | 401    | Ответ существующего protect     |
| Неожиданная ошибка базы или сервера | 500    | Объект с сообщением message     |

В ответе одно слово содержит `id`, `original`, `translation`, `sourceLanguage`, `targetLanguage`, `createdAt`, `updatedAt`. Сформируй этот объект явно: MongoDB хранит `_id`, а API отдаёт `id`, как в авторизации. В JSON идентификатор и даты представлены строками. Поля `user` и `__v` в ответ не включаем. Формат слова в POST и GET должен совпадать.

### Задание и стоп для ревью

Объясни, какие поля присылает клиент, какие назначает сервер и почему нельзя доверять `user` из тела запроса. Покажи выбранный контракт перед созданием модели.

## Шаг 2. Создать модель Word

### Идея

Посмотри на существующий `User.js`: там схема описывает поля, затем из неё создаётся и экспортируется модель. Здесь последовательность та же, но набор полей другой.

Поле `user` хранит ID владельца, а не весь объект пользователя. Для него нужен тип `Schema.Types.ObjectId`, обязательность и `ref` с именем существующей модели `User`. Сама ссылка не проверяет существование пользователя и не ограничивает доступ: отбор слов по владельцу мы напишем в контроллере.

### Задание

1. Создай папку `server/src/modules/word` и файл `Word.js`.
2. Опиши обязательное поле `user` по объяснению выше.
3. Опиши четыре обязательных строковых поля с удалением пробелов по краям.
4. Включи timestamps по образцу существующей модели пользователя. Даты вручную не присваивай.
5. Создай модель с именем `Word` и экспортируй её.

Проверки схемы дополняют проверки контроллера. Например, автоматическое преобразование значения в строку моделью не должно позволять API принимать число вместо текста.

### Стоп для ревью

Покажи только модель. Объясни разницу между `_id` слова и `user`: первый идентифицирует запись, второй — её владельца. Контроллер пока не пиши.

## Шаг 3. Проверить ввод перед сохранением

### Почему недостаточно проверки на пустое значение

Строка из пробелов не является пустой до удаления пробелов. Число, массив или объект тоже могут прийти в JSON. Вызов строкового метода у такого значения может завершиться ошибкой.

Поэтому порядок такой: проверить тип → убрать пробелы → проверить, что остался текст. Отсутствующее тело запроса или обязательное поле должны приводить к 400, а не к случайному исключению и ответу 500.

### Задание в word.controller.js

1. Создай асинхронный обработчик `createWord`.
2. Безопасно получи четыре разрешённых текстовых поля из тела запроса. Учти, что тело может отсутствовать или иметь неподходящий формат.
3. Проверь, что каждое поле — строка.
4. Удали пробелы по краям и проверь непустой результат.
5. При ошибке верни 400 с понятным `message` и сразу заверши обработчик.

На этом шаге проверяем только фрагмент валидации. Маршрут подключим после завершения сохранения, чтобы незаконченный обработчик не оставлял успешный запрос без ответа.

### Стоп для ревью

Покажи проверки. Объясни, что случится с отсутствующим полем, пустой строкой, строкой из пробелов и числом вместо строки. Проверь, что после ответа 400 выполнение не продолжается.

## Шаг 4. Сохранить слово и вернуть ответ

### Как назначается владелец

`protect` записал проверенный ID в `req.user.id`. Именно из него контроллер заполняет `user` при создании документа. Не копируй всё тело запроса в модель: клиент может прислать чужой ID или служебные поля.

### Задание

1. Импортируй модель Word в контроллер.
2. После успешной валидации сформируй данные явно: владелец из `req.user.id` и четыре обработанные строки.
3. Дождись результата `Word.create`.
4. Из сохранённого документа сформируй ответ по контракту шага 1.
5. Верни 201 и объект с полем `word` только после успешного сохранения.
6. Обработай ошибки: ошибку валидации Mongoose верни как 400, неожиданную ошибку — как 500. Технические подробности оставь в серверном логе, в ответе используй понятное сообщение.

Не возвращай успешный ответ до завершения записи. Данные ответа берём из результата базы, чтобы ID и даты соответствовали сохранённому документу.

### Стоп для ревью

Покажи завершённый `createWord`. Объясни, сможет ли клиент назначить слово другому пользователю, если добавит поле `user` в запрос, и что вернёт обработчик при сбое базы.

## Шаг 5. Подключить защищённый POST /words

### Как устроены пути

В `app.js` задаём общий префикс `/words`, поэтому внутри нового роутера путь создания — `/`. Если повторить `/words` в обоих местах, получится `/words/words`.

### Задание

1. Создай `word.routes.js` с Express Router.
2. Импортируй `createWord` из соседнего контроллера.
3. Импортируй существующий `protect` из соседнего модуля auth.
4. Зарегистрируй POST на `/`: сначала protect, затем createWord.
5. Экспортируй роутер и подключи его в `app.js` с префиксом `/words`, после middleware разбора JSON.
6. Запусти backend из папки `server` через `npm run dev`.

Относительный путь импорта считается от файла, в котором он написан. Внутри `modules/word` контроллер находится рядом, а middleware — в соседней папке `auth`.

### Проверка

В HTTP-клиенте получи токен через существующий `POST /auth/login`. Отправь `POST http://localhost:3000/words` с примером из шага 1 и этим токеном. Если используешь другой порт, подставь его.

Проверь 201, наличие ID и дат, затем отправь запрос без токена и запрос с пустым оригиналом. Ожидаются 401 и 400 соответственно. Неверные запросы не должны создавать документы.

### Стоп для ревью

Покажи импорты, подключение маршрута и результаты запросов без настоящего токена. Если сервер не запускается, сначала исправляем запуск, затем продолжаем.

## Шаг 6. Получить только свои слова

### Почему нельзя выбирать все документы

Проверка JWT отвечает на вопрос «кто отправил запрос». Она сама не добавляет фильтр к запросу MongoDB. Если вызвать поиск без условия владельца, пользователь получит чужие слова вместе со своими.

Фильтр должен использовать поле `user` и значение `req.user.id`. ID владельца из query-параметров или тела запроса для этого не нужен.

### Задание

1. В том же контроллере добавь асинхронный обработчик `getWords`.
2. Найди документы Word с владельцем, равным `req.user.id`.
3. Для понятного порядка отсортируй по `createdAt`: новые слова первыми.
4. Преобразуй каждый документ в тот же формат слова, который возвращает POST.
5. Верни 200 и объект с массивом `words`. Если документов нет, верни пустой массив, а не 404.
6. Неожиданную ошибку запроса к базе обработай ответом 500.
7. Подключи GET на `/` в роутере слов: сначала protect, затем getWords.

### Проверка и стоп для ревью

Выполни GET с токеном того же пользователя и найди созданное слово. Повтори запрос: чтение не должно создавать новые документы. Перезапусти backend и снова запроси список — слово должно сохраниться.

Покажи фильтр поиска и результат проверки. Объясни, почему успешного выполнения protect недостаточно для изоляции слов разных пользователей.

## Шаг 7. Проверить изоляцию на двух аккаунтах

### Подготовка

Используй два учебных аккаунта A и B. Для каждого получи собственный токен через вход. Храни токены в отдельных переменных HTTP-клиента, чтобы случайно не отправить оба запроса от одного пользователя. Токены и пароли в отчёт не вставляй.

### Задание

1. От имени A создай слово с узнаваемым оригиналом.
2. От имени B создай другое слово.
3. Запроси список от имени A: там должно быть его слово и не должно быть слова B.
4. Запроси список от имени B и проверь обратное.
5. С токеном A отправь ещё один POST, добавив в JSON поле `user` с ID аккаунта B. Слово должно принадлежать A, поскольку контроллер игнорирует присланного владельца.
6. Убедись через GET обоих пользователей, что это слово есть только у A.
7. Передай ID B в query-параметре GET от имени A: выборка должна по-прежнему определяться токеном A.

### Стоп для ревью

Сообщи результаты отдельно для A и B. Если обнаружились чужие слова, этап не завершён: сначала проверяем фильтр GET и назначение владельца в POST.

## Итоговая ручная проверка

| Сценарий                                                   | Ожидаемый результат                                  |
| ---------------------------------------------------------- | ---------------------------------------------------- |
| Корректный POST с токеном                                  | 201; одно слово сохранено, в ответе есть id и даты   |
| Пробелы вокруг оригинала и перевода                        | Сохраняется текст без пробелов по краям              |
| Отсутствует любое обязательное поле                        | 400; документ не создаётся                           |
| Пустая строка или только пробелы в любом обязательном поле | 400; документ не создаётся                           |
| Число, null, массив или объект вместо строки               | 400; документ не создаётся                           |
| POST без тела                                              | 400 при действительном токене; документ не создаётся |
| POST или GET без токена                                    | 401                                                  |
| POST или GET с недействительным токеном                    | 401                                                  |
| GET пользователя без слов                                  | 200; пустой массив words                             |
| GET после создания                                         | Возвращает сохранённое слово в согласованном формате |
| Повторный GET и GET после перезапуска backend              | Сохранённые данные доступны, чтение не создаёт копий |
| GET с токенами двух разных пользователей                   | Каждый видит только свои слова                       |
| В POST передан чужой user                                  | Владельцем остаётся пользователь из токена           |
| В GET передан чужой user в query                           | Список по-прежнему ограничен пользователем из токена |

После ошибочного POST сравни список с предыдущим: лишний документ не должен появиться. Реальную ошибку базы проверяем отдельно в тестовой среде; для ревью этого шага сначала достаточно проверить соответствующую ветку обработки ошибок, не отключая рабочую базу.
