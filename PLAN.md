# VocabLoop — учебный план разработки

Главная цель — научиться самостоятельно писать и понимать React, TypeScript, Node.js и Feature-Sliced Design. Рабочее приложение создаём постепенно, небольшими проверяемыми шагами.

## Как работаем

**Объяснение → план маленького шага → ты пишешь код → ревью → проверка → следующий шаг.**

- Наставник объясняет цель, нужные файлы, их роли и логику без готовой реализации.
- Код пишет ученик. Наставник не меняет его без прямой просьбы.
- При ошибке сначала объяснение и подсказка. Готовый код — только по прямому запросу.
- Каждый пункт этапа можно выполнять отдельно. После логического шага останавливаемся на ревью.
- Новые папки, абстракции и зависимости добавляем только при реальной необходимости.
- Этот документ — направление работы. Указанные будущие файлы не нужно создавать заранее.
- Redux Toolkit подключаем только при появлении обоснованной потребности в общем состоянии.

## Стек и результат

Frontend: React, TypeScript, Vite, FSD. Backend: Node.js на обычном JavaScript, Express, REST API, MongoDB.

Пользователь добавляет слово → frontend отправляет его backend → backend получает перевод через Groq API → сохраняет слово и перевод в MongoDB → frontend показывает список.

У слова доступно прослушивание оригинала и перевода. Из выбранных слов пользователь сохраняет Listening Session. Воспроизведение идёт по кругу: слово → перевод → пауза → следующее слово. Доступны запуск, пауза, остановка и настройка интервала.

Для перевода MVP используем Groq API на backend. Для озвучивания MVP используем Browser Web Speech API / SpeechSynthesis на frontend. Внешний платный TTS в MVP не подключаем. Перевод и озвучивание — отдельные задачи и интеграции. Генерацию примеров через AI рассматриваем позднее.

## Как применяем FSD

Направление импортов: `app → pages → widgets → features → entities → shared`. Верхний слой может использовать нижние, пропуская промежуточные. Слайсы одного слоя не импортируют друг друга напрямую.

| Слой       | Назначение в этом проекте                                                                  |
| ---------- | ------------------------------------------------------------------------------------------ |
| `app`      | Запуск React, провайдеры, маршруты, общие стили                                            |
| `pages`    | Полные экраны: вход, регистрация, слова, сохранённые сессии                                |
| `widgets`  | Крупные самостоятельные блоки, объединяющие сущности и действия; создаём при необходимости |
| `features` | Действия: добавить слово, сформировать сессию, управлять воспроизведением                  |
| `entities` | Данные и представление предметных сущностей: пользователь, слово, сессия                   |
| `shared`   | Общий HTTP-клиент, технические API-функции, ресурсы и независимые утилиты                  |

В слайсе `ui` содержит интерфейс, `model` — состояние и логику, `api` — запросы. Создаём только нужные разделы. `index.ts` задаёт публичные экспорты слайса.

Текущие формы можно оставить внутри страниц. Сам факт наличия формы не требует отдельной feature. `shared/api/auth.ts` пока остаётся адаптером HTTP API; логику переходов и состояния формы туда не переносим.

## Этап 1. Завершить базовую авторизацию

Цель: проверить вход, научиться проверять сессию на сервере и выходить из аккаунта.

1. Вручную проверить вход с правильным и неправильным паролем.
2. Подключить существующий контроллер `me` к защищённому `GET /auth/me` через `protect`.
3. Согласовать формат пользователя в ответе: `id`, `name`, `email`. Сейчас `me` возвращает документ с `_id`, а вход и регистрация — объект с `id`; привести ответы к одному контракту.
4. Добавить frontend-запрос текущего пользователя.
5. При открытии защищённой страницы проверять токен через backend. Различать ожидание, подтверждённый вход, ответ 401 и сетевую ошибку.
6. При 401 удалить недействительный токен и отправить на вход. Сетевую ошибку показать с возможностью повторить проверку.
7. Добавить выход: удалить токен и перейти на страницу входа.

Файлы:

- `server/routes/authRoutes.js` — маршрут получения текущего пользователя.
- `server/controllers/authControler.js` — единый формат ответа пользователя.
- `server/middleware/authMiddleware.js` — серверная проверка JWT; уже существует.
- `client/src/shared/api/auth.ts` — запрос текущего пользователя и тип ответа.
- `client/src/app/router/ProtectedRoute.tsx` — ожидание проверки и решение о доступе к странице.
- `client/src/pages/home/ui/HomePage.tsx` — временное место для кнопки выхода.

Проверка: вход, обновление защищённой страницы, выход, отсутствие токена, недействительный токен, недоступный backend. Наличие строки в localStorage само по себе не доказывает, что пользователь авторизован.

## Этап 5. Перевод через Groq API

Цель: пользователь вводит слово и языки, а перевод получает backend.

1. Подготовить интеграцию Groq API: перед реализацией изучить актуальную документацию, выбрать доступную LLM, создать API-ключ и проверить лимиты Free tier. Подробности — в [STAGE-5-TRANSLATION.md](./STAGE-5-TRANSLATION.md).

3. Создать отдельный сервис перевода. Учётные данные Groq использовать только на backend через конфигурацию окружения; не помещать секреты в frontend или репозиторий.
4. Изменить `POST /words`: проверить ввод → запросить перевод → проверить ответ Groq API → сохранить документ → вернуть слово.
5. Обработать тайм-аут, ошибку провайдера и некорректный ответ. Не сохранять незавершённое слово как успешный результат.
6. Убрать обязательный ручной перевод из формы; добавить выбор языков и состояние ожидания перевода.

Файлы:

Проверка: реальный перевод сохраняется и появляется в списке; сбой сервиса перевода виден пользователю; учётные данные отсутствуют в frontend. Генерацию примеров оставляем на будущее.

## Этап 9. Циклический плеер сессии

Цель: управляемый цикл «слово → перевод → пауза → следующее слово».

1. Сначала описать состояния: остановлен, воспроизводится, на паузе; текущий индекс и текущая фаза.
2. Реализовать один проход по словам, используя сигнал окончания TTS.
3. После последнего перевода и паузы возвращаться к первому слову.
4. Добавить паузу и продолжение. До реализации определить поддерживаемое поведение SpeechSynthesis в целевых браузерах: продолжение реплики или её повторный запуск. Во время межсловной паузы сохранять оставшееся время.
5. Добавить Stop: отменить речь и таймер, сбросить индекс на начало.
6. Использовать сохранённый интервал сессии; решить, что новое значение применяется к следующей паузе.
7. При смене сессии, изменении её состава или уходе со страницы останавливать старый цикл.
8. Защитить цикл от устаревших асинхронных завершений после Stop и повторного Play.
9. Не запускать пустую сессию; при ошибке TTS остановить цикл и показать сообщение.

Файлы:

- `features/play-listening-session/model/useSessionPlayer.ts` — состояние плеера, порядок реплик, таймеры и отмена.
- `features/play-listening-session/ui/SessionPlayer.tsx` — Play, Pause, Stop, текущий прогресс.
- `features/play-listening-session/index.ts` — публичный экспорт плеера.
- `shared/lib/tts/speech.ts` — общая техническая озвучка; обе features используют её независимо.
- `pages/listening-session/ui/ListeningSessionPage.tsx` — передаёт плееру слова и настройки.

Это feature, потому что реализует действие пользователя. Если позже весь блок сессии станет крупной самостоятельной композицией, обсудим выделение widget. Глобальное воспроизведение между страницами пока не требуется.

Проверка: один элемент, несколько элементов, повтор цикла, пауза во время речи и ожидания, продолжение, Stop, повторный Play, смена страницы, ошибка TTS. Для отмены и переходов состояний полезны небольшие автоматические тесты с подменой TTS и таймеров.

## Этап 10. Проверить полный пользовательский сценарий

1. Зарегистрироваться и войти.
2. Добавить несколько слов с переводом через Groq API.
3. Обновить страницу и увидеть сохранённые слова.
4. Прослушать отдельное слово и перевод.
5. Выбрать слова и сохранить Listening Session.
6. Изменить её состав и интервал, сохранить и открыть повторно.
7. Запустить цикл, поставить на паузу, продолжить и остановить.
8. Выйти и войти снова: слова и сессии сохранены.
9. Проверить разделение данных двух пользователей.
10. Выполнить проверку TypeScript, линтер и сборку. Описать запуск frontend, backend и необходимые переменные окружения в README без секретов.
