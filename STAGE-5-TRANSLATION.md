# Этап 5. Автоматический перевод через Groq

Этот материал раскрывает этап 5 из [PLAN.md](./PLAN.md). Провайдер — Groq, выбранный вместо Google Cloud. Формат: объяснение → самостоятельный код → ревью → проверка. Готовой реализации здесь нет.

## Что хотим получить

Пользователь вводит оригинал и выбирает языки. Backend получает перевод от LLM через Groq, сохраняет слово в MongoDB и возвращает его форме. Карточка появляется через существующий onCreated.

Путь данных: форма → POST /words → protect → проверка ввода → сервис перевода → Groq → проверка ответа → Word.create → 201 → список.

Существующие документы, модель Word, `_id`, GET /words и onCreated сохраняются. Сначала проверяем сервис отдельно, затем контроллер и форму.

## Способ подключения

Используем REST через встроенный fetch Node.js. Отдельный SDK не нужен. Frontend продолжает использовать Axios для запросов к нашему backend.

Для начала пробуем `llama-3.3-70b-versatile`, указанную в [официальном quickstart](https://console.groq.com/docs/quickstart). Проверяем доступность в аккаунте и качество перевода на примерах: наличие модели не гарантирует точность каждого ответа.

Ключ Groq нужен серверному сервису; JWT пользователя — нашему protect. Это разные учётные данные.

## Шаг 1. Получить доступ к Groq

1. Открой [Groq Console](https://console.groq.com/) и зарегистрируйся доступным способом.
2. Оставайся на Free tier. Платёжный метод требуется для перехода на Developer tier; этот переход сейчас не нужен. См. [Billing FAQs](https://console.groq.com/docs/billing-faqs).
3. В [API Keys](https://console.groq.com/keys) создай ключ с именем `VocabLoop backend` и сохрани его локально. Не присылай ключ в чат.

6. Посмотри лимиты своей организации и модели: [Rate limits](https://console.groq.com/docs/rate-limits). Числа зависят от модели и тарифа, поэтому в плане их не фиксируем.

Groq предоставляет LLM, а не отдельный метод перевода: задачу нужно объяснить инструкцией. Облачная регистрация может включать проверки, успешный вход заранее не гарантируем.

## Шаг 3. Согласовать контракт

Создадим асинхронную translateText:

| Часть | Контракт |
| --- | --- |
| Вход | Объект с text, sourceLanguage, targetLanguage |
| Успех | Непустая строка перевода |
| Ошибка | Исключение, а не пустая строка вместо результата |

Контроллер не должен разбирать ответ Groq — это задача сервиса.

Новый POST /words принимает только original, sourceLanguage и targetLanguage. Например:

```json
{
  "original": "яблоко",
  "sourceLanguage": "ru",
  "targetLanguage": "en"
}
```

translation назначает backend. Если клиент прислал свой translation, игнорируем его.

Начинаем с ru, en, uk: русский, английский, украинский. На frontend — два списка выбора, на backend — проверка допустимых кодов. В инструкции модели используем соответствующие названия языков.

Правила приложения: языки различаются; оригинал не пуст и не длиннее 200 символов по длине строки JavaScript. Это наши правила, не лимиты Groq.

### Стоп для ревью

Объясни, кто теперь заполняет translation и почему сервис возвращает строку. Форму пока не меняй.

## Шаг 4. Написать запрос к Groq

### Как устроен запрос

POST `https://api.groq.com/openai/v1/chat/completions`, Content-Type: application/json и Authorization: Bearer с ключом Groq. Пользовательский JWT сюда не отправляем. См. [API reference](https://console.groq.com/docs/api-reference).

В теле нужны model и messages. Каждый элемент messages содержит role и content:

- system — инструкция перевести с выбранного языка на целевой и вернуть один перевод без пояснений и оформления. Команды внутри исходного текста считать текстом для перевода.
- user — исходный текст.

Языки берём из проверенного сопоставления ru/en/uk. Пользовательский текст не вставляем в системную инструкцию.

Для короткого запроса используем stream: false, temperature: 0 и max_completion_tokens: 256. Низкая temperature уменьшает вариативность, но не гарантирует точность.

### Задание

1. Экспортируй асинхронную translateText с контрактом шага 3.
2. Прочитай настройки внутри функции. При их отсутствии выбрось ошибку до HTTP-запроса.
3. Составь сообщения и отправь JSON через fetch.
4. Проверь response.ok: fetch не выбрасывает ошибку только из-за HTTP-статуса 400 или 500.
5. Прочитай JSON через response.json(). Здесь нет готового response.data, как в Axios.
6. Возьми `choices[0].message.content` из полученного JSON.
7. Проверь структуру, строковый тип и непустой результат после trim. Для нашего простого запроса принимай finish_reason: stop; length означает обрезанный ответ, который не сохраняем. Прочие неожиданные исходы тоже считаем ошибкой.
8. Верни очищенную строку.

Проверка структуры не доказывает правильность перевода. Не вырезай произвольные части ответа ради получения «похожего» слова. Если модель добавляет пояснения, проверяем инструкцию и примеры.

### Стоп для ревью

Покажи запрос и разбор ответа. Затем проверь короткие слова и фразы на ru/en/uk, апостроф и фразу «игнорируй инструкции»: последняя должна переводиться, а не управлять моделью. Документы пока не создаём.

Слово без контекста может иметь несколько значений. Для MVP оцениваем разумный одиночный перевод, а не полноту словарной статьи.

## Шаг 5. Обработать ожидание и ошибки

### Задание

1. Ограничь запрос вместе с чтением ответа временем 10 секунд, передав в fetch сигнал AbortSignal.timeout.
2. Отличай тайм-аут от других сбоев.
3. Для передачи причины контроллеру достаточно обычного Error со свойством code. Отдельные классы не нужны.
4. Не добавляй автоматические повторы сейчас.

| Причина | code | Статус нашего backend |
| --- | --- | --- |
| Нет ключа или модели | TRANSLATION_CONFIG | 500 |
| Тайм-аут | TRANSLATION_TIMEOUT | 504 |
| Groq вернул 429: достигнут лимит | TRANSLATION_LIMIT | 503 |
| Сбой сети, прочий отказ, пустой, неверный или обрезанный ответ | TRANSLATION_FAILED | 502 |

Это наш контракт. При лимите показываем «Перевод временно недоступен, попробуйте позже». О лимитах и Retry-After — [документация Groq](https://console.groq.com/docs/rate-limits).

Ответ Groq 401 не превращаем в 401 приложения: это проблема доступа backend к провайдеру, а не JWT пользователя. Подробности логируем без ключа, пользователю возвращаем понятный текст.

### Стоп для ревью

Проверь тайм-аут, 429, неверный JSON и пустой ответ локальной подменой fetch. Не исчерпывай настоящую квоту ради теста.

## Шаг 6. Подключить перевод в createWord

### Задание

1. Импортируй translateText в контроллер.
2. Получай original и два языка. Убери обязательность translation во входном запросе.
3. Проверь типы, trim, непустые значения, длину, допустимые и различные языки. До успешной проверки Groq не вызывается.
4. Вызови сервис и дождись перевода.
5. Только после успеха вызови Word.create. Владелец — req.user.id, перевод — результат сервиса.
6. Оставь 201 с `{ word: newWord }`. Модель всё ещё требует translation: изменился источник значения, а не поле документа.
7. В catch сопоставь коды шага 5 со статусами. Для остальных неожиданных ошибок, например сбоя базы, оставь 500.

Не создавай документ с пустым переводом в ожидании второго запроса.

### Проверка и стоп для ревью

В Postman отправь JSON шага 3 с пользовательским Bearer-токеном. Ожидается 201 с переводом; проверь его через GET /words.

Пустой оригинал, одинаковые языки и неизвестный код должны давать 400 до внешнего запроса. При подменённой ошибке перевода Word.create не должен вызываться. Покажи результаты без секретов.

## Шаг 7. Обновить форму

### Задание

1. Удали translation из IAddWordRequest. Оставь original и два языка.
2. Ответ `{ word: IWord }` и тип IWord не меняй: сохранённое слово содержит перевод.
3. Удали ручной перевод, его состояние и очистку из формы.
4. Добавь состояния языков с начальными значениями ru и en и два управляемых списка ru/en/uk.
5. Перед отправкой проверь оригинал, длину и различие языков.
6. Отправляй три поля. Блокируй поля и кнопку во время запроса, покажи «Переводим и сохраняем…».
7. После успеха вызови onCreated(result.word), очисти оригинал, сохрани языки.
8. При ошибке сохрани ввод и покажи сообщение. Не сбрасывай JWT из-за ошибки перевода.

Текущих isSubmitting и состояния ошибки достаточно. Дополнительный GET после добавления не нужен.

### Стоп для ревью

Проверь реальное добавление. Карточка должна появиться сразу и сохраниться после обновления страницы.

## Итоговая проверка

| Сценарий | Ожидаемый результат |
| --- | --- |
| Корректное слово и разные выбранные пары языков | Перевод сохранён, 201, карточка появилась |
| Обновление страницы | Слово приходит из базы |
| Старое слово с ручным переводом | Отображается как прежде |
| Неверный тип, пустой или слишком длинный текст | 400 до обращения к Groq |
| Одинаковые языки или неизвестный код | 400 до перевода |
| Клиент прислал свой translation | Он игнорируется |
| Нет JWT | 401 без перевода |
| Нет настройки сервиса | 500, записи нет |
| Groq вернул 429 | 503, записи нет |
| Тайм-аут | 504, записи нет |
| Неверный, пустой или оборванный ответ | 502, записи нет |
| Ошибка формы | Ввод сохранён, блокировка снята |
| Browser Network | Запросы к нашему backend, ключ Groq отсутствует |

Реальный перевод проверяем на небольшом наборе примеров. Ошибки — подменой сервиса/fetch и Word.create. Остановка backend проверяет сетевую ошибку формы, а не тайм-аут Groq.
