# Этап 1. Понять и завершить авторизацию

Этот материал раскрывает этап 1 из [PLAN.md](./PLAN.md). Работаем в существующей структуре: перенос backend в `src` будет следующим этапом.

Формат работы: читаешь объяснение одного шага → пишешь небольшой фрагмент самостоятельно → просишь ревью → проверяешь поведение → переходишь дальше. Ниже нет готовой реализации.

## Что хотим получить

После входа пользователь открывает свою страницу. После обновления страницы приложение проверяет сохранённый токен через backend. Если проверка успешна, страница остаётся доступной. Если вход больше недействителен, приложение возвращает на логин. Если сервер временно недоступен, показывает ошибку и повтор проверки. Пользователь также может выйти.

## Почему одного login недостаточно

При входе сервер получает email и пароль, проверяет их и возвращает токен вместе с данными пользователя. Твой frontend сохраняет токен в localStorage.

После обновления страницы состояние React создаётся заново, а localStorage сохраняется. Приложение видит строку токена, но ещё не знает, действительна ли она сейчас.

Текущий ProtectedRoute проверяет только наличие строки. Это проверка интерфейса, а не подтверждение входа сервером. Произвольная непустая строка тоже позволит отобразить страницу, но защищённый backend должен отклонить запрос с такой строкой.

`GET /auth/me` означает «верни текущего пользователя». Мы не повторяем проверку пароля: отправляем токен, который сервер выдал после входа.

Отдельный маршрут me — удобный способ проверить текущий вход и получить профиль. Он не обязателен для любого приложения, но подходит нашему сценарию. Он не заменяет проверку токена на маршрутах слов и сессий.

## Слова, которые встретятся

| Понятие       | Что означает у нас                                                            |
| ------------- | ----------------------------------------------------------------------------- |
| JWT           | Подписанный сервером токен с данными, включая ID пользователя и срок действия |
| Проверка JWT  | Проверка подписи и срока действия; простого чтения содержимого недостаточно   |
| Authorization | Заголовок HTTP-запроса, через который отправляем токен                        |
| Bearer        | Обозначение схемы: после него через пробел идёт токен                         |
| Middleware    | Функция Express, выполняющаяся перед следующим обработчиком                   |
| Controller    | Обработчик конкретного запроса: получает данные и формирует ответ             |
| req           | Объект текущего запроса                                                       |
| res           | Объект, через который сервер отправляет ответ                                 |
| next          | Передаёт обработку следующей функции в цепочке Express                        |
| 401           | Сервер не подтвердил вход                                                     |
| 500           | Внутренняя ошибка сервера; сама по себе не означает неправильный токен        |

JWT не является зашифрованным хранилищем пароля. В нашем проекте пароль не помещается в токен. Токен не публикуем и не вставляем в отчёты о проверке.

## Как связаны файлы

Все пути ниже относительно корня проекта.

| Файл                                       | Роль на этом этапе                                              |
| ------------------------------------------ | --------------------------------------------------------------- |
| `server/routes/authRoutes.js`              | Связывает адрес запроса с protect и me                          |
| `server/middleware/authMiddleware.js`      | Проверяет токен и записывает проверенный ID в req.user          |
| `server/controllers/authControler.js`      | Содержит login, register и me; me получает пользователя из базы |
| `server/models/User.js`                    | Описывает документ пользователя в MongoDB                       |
| `server/app.js`                            | Подключает auth-маршруты с префиксом /auth                      |
| `client/src/shared/api/api.ts`             | Общий Axios-клиент, добавляющий сохранённый токен к запросам    |
| `client/src/shared/api/auth.ts`            | Типы и HTTP-запросы авторизации; добавим запрос me              |
| `client/src/app/router/ProtectedRoute.tsx` | Управляет доступом к странице и состоянием проверки             |
| `client/src/pages/home/ui/HomePage.tsx`    | Временное место для кнопки выхода                               |

По FSD: HTTP-адаптер остаётся в shared/api, решение о доступе к маршруту — в app, кнопка выхода пока принадлежит странице. Redux, новый widget и отдельная entity пользователя для этой маленькой задачи не требуются. Файлы не переносим одновременно с изменением поведения.

## Шаг 1. Проверить уже написанный вход

### Задание

1. Запусти backend и frontend.
2. Войди с зарегистрированным email и правильным паролем.
3. Убедись, что открывается домашняя страница.
4. Открой страницу входа и проверь неправильный пароль: должно появиться сообщение об ошибке.

Вход с неправильным паролем не обязан удалять токен от предыдущего успешного входа. Для чистой проверки используй отдельное приватное окно или удали только ключ token в инструментах браузера.

### Стоп для ревью

Сообщи результат этих двух сценариев. Если backend не запускается, сначала выполни шаг 2: при подготовке этого документа в маршруте обнаружены отсутствующие импорты.

## Шаг 2. Связать маршрут, protect и me

### Что уже есть и что сейчас мешает

В `authRoutes.js` уже добавлен GET-маршрут `/me` с обработчиками protect и me. Но они не импортированы: из контроллера импортируются только login и register, а middleware не подключён.

Использование необъявленного имени при создании маршрута приводит к ошибке запуска backend. Это нужно исправить прежде, чем проверять запрос.

### Как проходит запрос

Frontend → GET /auth/me с токеном → protect → me → ответ с пользователем.

У Express префикс `/auth` уже задан в app.js, поэтому внутри authRoutes.js нужен только путь `/me`.

### Разбираем protect

1. Читает заголовок Authorization.
2. Если заголовка нет или нет ожидаемого начала Bearer, отправляет 401 и завершает обработку.
3. Извлекает токен из заголовка.
4. Проверяет токен через jwt.verify с серверным секретом.
5. При успехе записывает ID в req.user.
6. Вызывает next, чтобы Express запустил me.
7. При ошибке проверки отвечает 401, не вызывая me.

req.user — добавленное нашим middleware поле, оно не появляется в Express автоматически. Оно существует для текущего запроса и не является общей переменной для всех пользователей.

### Задание

1. В authRoutes.js дополни импорт из контроллера именем me.
2. Добавь именованный импорт protect из существующего файла middleware.
3. Сохрани порядок обработчиков: сначала protect, затем me.
4. Проверь запуск backend.

Не меняй алгоритм JWT и не переписывай контроллеры на этом шаге.

### Проверка понимания и ревью

Объясни своими словами: почему me нельзя поставить перед protect и откуда берётся req.user.id? Затем попроси проверить импорты и маршрут.

## Шаг 3. Разобрать me и согласовать ответ

### Что делает существующий код

1. Берёт ID из req.user, заполненного middleware.
2. Через User.findById ищет документ пользователя в MongoDB.
3. select с исключением password не включает хеш пароля в выбранные данные.
4. Если пользователь отсутствует, сейчас возвращает 404.
5. Если найден — возвращает объект с полем user.
6. При неожиданной ошибке возвращает 500.

Валидная подпись токена не доказывает, что пользователь всё ещё существует: его могли удалить после выдачи токена. Поэтому поиск в базе имеет смысл.

### Два изменения контракта

**Формат пользователя.** Сейчас me возвращает документ MongoDB с `_id`, а login и register возвращают `id`, `name`, `email`. Для frontend нужен одинаковый формат.

**Пользователь не найден.** Для нашего маршрута текущего входа договоримся возвращать 401, если пользователь по токену больше не существует. Так frontend одинаково завершает недействительный вход. Это выбранный контракт нашего приложения; 404 в скопированном коде не является универсальной ошибкой, но потребовал бы отдельной обработки.

### Задание

1. В me сформируй user явно из трёх полей: id, name, email, по образцу уже существующего ответа login.
2. В ветке отсутствующего пользователя верни 401.
3. Сохрани ответ 500 для неожиданной ошибки базы или сервера.
4. Не возвращай пароль и не добавляй выдачу нового токена в me.

Ответ me содержит user. Ответ login содержит user и token. Поэтому на frontend им понадобятся разные типы ответа.

### Проверка и ревью

Проверь запрос без токена: ожидается 401. После подключения frontend отдельно проверим успешный ответ. Не присылай настоящий токен для ревью.

## Шаг 4. Добавить frontend-запрос текущего пользователя

### Идея

Функция HTTP-запроса знает адрес и формат данных. Она не должна показывать Alert, менять маршрут или управлять состоянием React — этим займётся ProtectedRoute.

### Задание в shared/api/auth.ts

1. Добавь тип ответа текущего пользователя, например CurrentUserResponse. Внутри только user с уже существующим типом AuthUser.
2. Добавь асинхронную функцию getMe без аргументов.
3. Через общий api выполни GET на `/auth/me` с типом ответа.
4. Верни response.data, как в существующих функциях входа и регистрации.
5. Не перехватывай ошибку ради возврата пустого пользователя: вызывающий код должен отличать успех от сбоя.

В api.ts уже есть перехватчик запроса: он читает token из localStorage и добавляет Authorization. Не нужно повторять эту работу внутри getMe.

### Стоп для ревью

Проверь, что getMe не принимает email, пароль или ID, а её тип не обещает новый token. Попроси проверить функцию перед подключением к React.

## Шаг 5. Проверять вход в ProtectedRoute

### Почему нужна проверка с состояниями

Запрос не завершается мгновенно. Пока ответ неизвестен, нельзя ни показывать защищённую страницу, ни считать пользователя вышедшим.

Вместо нескольких несвязанных флагов удобно одно состояние status с четырьмя значениями:

| Состояние       | Что отображаем                                   |
| --------------- | ------------------------------------------------ |
| checking        | Сообщение «Проверяем вход…»                      |
| authenticated   | Переданные children, то есть защищённую страницу |
| unauthenticated | Переход на /login                                |
| error           | Сообщение о сбое и кнопку повторной проверки     |

### Последовательность

Открытие защищённого маршрута → checking → чтение токена.

- Токена нет → unauthenticated, запрос не нужен.
- Токен есть → вызвать getMe.
- Успешный ответ → authenticated.
- Ответ 401 → удалить token → unauthenticated.
- Сетевая ошибка или 500 → error, токен сохранить.

Сбой соединения не доказывает, что вход недействителен. Поэтому нельзя удалять токен в любом catch.

### Маленькие задания

1. Добавь status и отображение четырёх состояний. Начинай с checking.
2. Запускай первоначальную проверку в useEffect, а не прямо во время рендера.
3. Внутри эффекта объяви асинхронную функцию и вызови её. Сам callback эффекта не делай async: React ожидает от него функцию очистки или отсутствие результата, а не Promise.
4. Подключи getMe и переходы при успехе и ошибке.
5. Для проверки HTTP-статуса сначала уточни, что ошибка принадлежит Axios, через его проверку isAxiosError. В TypeScript значение из catch нельзя без проверки считать объектом с response.status.
6. Добавь очистку эффекта, чтобы завершение старого запроса не меняло состояние после ухода со страницы. Для этого достаточно локального признака отмены; проверь его перед изменениями состояния и удалением токена.
7. После ревью основной проверки добавь повтор: кнопка меняет счётчик попыток, эффект зависит от него и начинает новую проверку с checking. Так начальная и повторная проверка используют одну последовательность.

Не помещай status в зависимости эффекта, если сам эффект его обновляет: можно случайно организовать повторяющиеся запросы. Все хуки вызывай до условных возвратов компонента.

В режиме разработки StrictMode может повторно запускать эффект с очисткой. Не отключай его ради скрытия повторного GET: запрос чтения и очистка должны выдерживать повторный запуск.

Данные user пока можно не сохранять отдельно, если домашняя страница их не отображает. Проверка ответа уже подтверждает доступ. Когда понадобится имя в нескольких местах, отдельно обсудим хранение текущего пользователя.

### Стоп для ревью

Сначала покажи первоначальную проверку и ветки отображения. После ревью добавь очистку и повтор. Не требуется писать весь шаг за один подход.

## Шаг 6. Добавить выход

### Задание в HomePage.tsx

1. Добавь кнопку «Выйти» и её обработчик.
2. Удали из localStorage только ключ token. Не используй clear: он удалит и другие настройки приложения.
3. Перейди на `/login`, заменив текущую запись истории.

Для нашего текущего JWT-подхода отдельный backend-маршрут выхода пока не нужен. Это локальный выход: браузер перестаёт хранить и отправлять токен. Уже выданный токен сам по себе не отзывается на сервере и остаётся действительным до истечения срока. Отзыв токенов и refresh-токены — отдельная будущая тема.

### Стоп для ревью

Проверь обработчик выхода. Затем нажми «Назад» и попробуй снова открыть защищённый URL: доступ не должен восстановиться без входа.

## Итоговая ручная проверка

| Сценарий                                   | Ожидаемый результат                                         |
| ------------------------------------------ | ----------------------------------------------------------- |
| Верный email и пароль                      | Токен сохранён, /auth/me успешен, домашняя страница открыта |
| Неверный пароль                            | Ошибка формы входа, перехода после запроса нет              |
| Обновление домашней страницы               | Проверка входа, затем страница                              |
| Открытие защищённого URL без token         | Переход на /login                                           |
| Произвольная строка вместо token           | 401, удаление строки, переход на /login                     |
| Backend недоступен при проверке            | Сообщение и повтор; токен сохранён                          |
| Backend снова доступен, нажат повтор       | Новая проверка, затем страница                              |
| Выход и повторное открытие защищённого URL | Переход на /login                                           |
| Успешный ответ me                          | user содержит id, name, email; password отсутствует         |

Запросы и статусы удобно смотреть во вкладке Network инструментов браузера. Для тестов используй учебный аккаунт. Проверку удалённого пользователя выполняй только на специально созданном тестовом аккаунте, если отдельно решим проверить этот случай.
